## Repository conventions

- Laravel **12.69.2**, PHP **8.3.36** in the Composer platform, MySQL, Eloquent and Blade. Frontend: Vite, Tailwind 4, Alpine; public design tokens and components already exist. Admin uses the separate BlatUI/Turbo bundle and `x-admin.*` adapters described in `docs/admin-ui.md`.
- Applicable `CONTRIBUTING.md` requires categorized branches, explicit-path Pint, design-system lint, language parity and relevant PHPUnit/Playwright checks. It refers to a local-only `AGENTS.md`, but no such file was available in this checkout or the workspace ancestors inspected; no missing instructions have been invented.
- Public/owner routes use `/{locale}`, `setLocale`, `lroute()` and the existing canonical-host helpers. New specific paths must precede the generic static-page route. Private application/management pages need no-cache/noindex and normal authenticated CSRF-protected forms. Existing public stateless/session and edge-cache behavior must be respected.
- Personal login uses `web`; administration uses the separate `admin` guard over the same `User` model. `admin_can()` and `permission:module,action` consult the existing role/permission matrix; system roles already have full access. Add an organization module, not an account-type column or a new login system.
- Validation belongs in FormRequests or existing request validators. Existing petition ownership checks are inline controller/request rules, not an existing `PetitionPolicy` class. Organization authorization should be explicit and isolated without changing those existing checks.
- ISO country validation already exists in `App\Support\Countries`. Existing foreign IDs use unsigned bigint-compatible IDs. Status/type values can follow the current validated-string/constant conventions.
- Tests use PHPUnit 11.5, factories, SQLite/`RefreshDatabase`, mail/storage fakes, and Playwright with accessibility/visual coverage. File-upload admin forms use `data-turbo="false"`. Pint must not run indiscriminately through the WordPress vendor tree.
- Public UI text lives in `lang/`. Provide en/fr/it organization copy; the other active locales can explicitly load the English organization file so the existing parity audit remains valid. Organization JSON tagline/description needs the specified current-locale → English → first nonempty fallback, rather than blindly copying relational petition translations.

## Petitions, signatures and categories

- `petitions.user_id` remains the personal author. Account deletion currently preserves petitions by nulling that relationship; adding an organization must not transfer authorship, exports or edit permissions.
- Public eligibility is `Petition::visible()`: `status = published` and `is_active = 1`. Draft/held/inactive content cannot enter organization public grids or totals.
- The content editor is owner-only and becomes unavailable after another person's confirmed, non-spam signature. Later outcome management must distinguish author authorization from that content-editability restriction: recording a result must not unlock petition text.
- `PetitionSigning` owns guest/authenticated signing and verification. Guest verification follows the current configurable email-verification rules. It prevents guests from impersonating existing verified accounts and uses generic responses. `markVerified()` confirms only eligible pending, non-spam signatures in a transaction.
- **Selected counter strategy:** reuse `petitions.signature_count`. `PetitionStats` updates counts transactionally, invalidates caches, recalculates after moderation, and has a scheduled reconciliation command using `confirmed = 1 AND is_spam = 0`. Organization totals will sum counters from currently public linked petitions. No raw-signature aggregation on public requests and no additional organization total-cache column is planned unless a concrete reliability issue is found.
- Existing `categories`/`category_translations` remain separate and untouched. The 20 closed causes in v6 will have their own idempotent seed and unique pivot pairs; no historical reclassification.

## Uploads, links, audit and email

- Intervention Image **3.11.9**, Laravel integration and GD are already installed. Existing uploads have a 40-megapixel input guard and use public storage/variant helpers. Organization processing must explicitly re-encode, strip metadata and discard animation; global image configuration currently does **not** strip metadata, so reusing its defaults unchanged would be wrong.
- Use the v6 limits (logo 2 MB/400×400; cover 3 MB/1500×500), vertical focal choices and deterministic missing-image presentation. Save replacement files before committing references, and remove old/unreferenced files after a successful change. No uploaded SVG or new crop/preview interface.
- Public website, donation and social values must be parsed/validated without fetching their destinations. Social domain checks use exact/dot-boundary matching, not substrings. Donation changes clear approval. The IT tax-code block follows v6's uppercase alphanumeric/max-16 definition; validation is not a claim of 5×1000 eligibility.
- `AdminAuditLog` and `AppLog` exist, but generic application logs are pruned after 30 days. A small organization event history is justified for state changes, original declarations/terms actor and owner reassignment. Private references/review notes must also be kept out of generic request-input logs visible to unrelated log permissions. Tokens must never enter audit payloads.
- Existing mail uses localized `MailText`, editable templates, database queues and quota gates; explicit `afterCommit()` is required because the queue connection does not enable it globally. Existing contact routing uses `email_to_staff` with the configured sender as fallback. Organization support/admin addresses must be confirmed/configured before launch, not invented in UI.
- Current quota middleware may drop nontransactional messages and defer transactional ones. Phase 3 must select the proper behavior for each organization transactional message. No new provider, purchase or follower-delivery system is part of v6 phases 1–3.

## Approved owner-account deletion rule

**Owner account deletion:** Organizations belongs exclusively to the Laravel platform. The magazine is an independent editorial WordPress installation with staff administrators; do not model platform users as magazine users or couple the new organization lifecycle to WordPress. The new owner foreign key must not block Laravel account deletion or cascade-delete organizations.

Approved by the project owner on 2026-11-07: preserve the organization and its history, suspend it, clear the deleted owner's reference and require administrator reassignment/review before restoring public access. Use a nullable owner reference for this exceptional state; never cascade-delete the organization.

Implementation requirements for phase 1:

- Suspend every organization owned by the departing user, including pending/rejected organizations, and remove public profile eligibility immediately.
- Perform organization suspension, owner-reference clearing, event recording and Laravel account deletion together in a database transaction. Leave magazine accounts, configuration and editorial data outside this feature. The current bulk User deletion does not fire model observers; an observer alone is insufficient.
- Retain organization identity, first verification, founding recognition, campaigns, historical consents and original terms/declaration evidence. Do not transfer personal petition authorship or introduce new deletion of historical records.
- Keep a dedicated event with the former owner ID and a system reason code; do not retain deleted-account contact details in that event.
- Permit only an authorized administrator to assign an existing replacement user. Reassignment alone must not silently make a suspended organization public: restoration requires the normal admin review action.
- Cover multiple owned organizations, rollback on failure, the public 404 state, reassignment and preservation of existing personal-petition permissions in phase-1 tests.

Other documented assumptions: preserve the first verification timestamp for identity locking; restore previously verified suspended organizations only after admin review; profile edits remain moderated, with explicit preapproval for donation destinations. No database change is needed for future follower delivery in this MVP.


## Phase-one implementation and operation

- Public landing: `/{locale}/organizations`; terms: `/{locale}/organizations/terms`; public verified profile: `/{locale}/org/{slug}`. Nonverified or ownerless profiles return 404. Phase one shows zero linked petitions/signatures and an honest empty campaign state; petition integration remains phase two.
- Authenticated personal account, complete profile and CSRF are required for application, dashboard, profile updates and resubmission. Management routes are under `/org/{slug}/manage`, `/manage/profile` and `/manage/resubmit`. Other users cannot access private evidence. Suspended profiles are read-only.
- Admin: `/admin/organizations`, searchable/paginated with state filter; `/admin/organizations/{id}` for private evidence, original terms acceptance, current applicant and event history. Existing `organizations:view` and `organizations:edit` permissions apply. System administrators already have access; grant delegated roles explicitly through the existing permission screen. Do not rerun role/permission reset seeders on production.
- Review identity and representative authority manually. Verify/reject/suspend/restore all require confirmation and a private note. First verification timestamp stays fixed; name/legal name/type/country are then owner-locked, and the public slug stays immutable. Admin can correct identity without changing the slug. Founding recognition is a separate confirmed administrative toggle, never an economic entitlement.
- Donation URLs remain hidden until a confirmed admin approval of the exact displayed URL. Every owner URL change clears both approval fields. All links require HTTPS, no credentials/custom ports; social domains use exact or dot-boundary matching. No submitted URL is fetched. Donations are external and the profile explains that FreeCause processes no payment.
- Tax code is optional, uppercase alphanumeric, max 16; the public 5×1000 section appears only for Italy with a code. Validation does not certify eligibility.
- Uploads reuse installed Intervention/GD: logo 400×400, max 2 MB; cover 1500×500, max 3 MB; real MIME/dimensions, 40 MP decoded-input limit, orientation, metadata stripping, animation discarded, WebP output. Cover uploads also generate the existing 400w/800w responsive variants; the profile and its preload use matching srcsets, while social sharing retains the 1500×500 image. No originals retained. To change an existing cover crop, upload its source again and select top/center/bottom; this avoids retaining an additional private original solely for recropping. Replace/remove deletes old files only after a successful database change. No arbitrary crop/preview UI.
- Owner deletion is integrated into both Laravel self-deletion and the existing admin deletion path. Suspension, owner clearing, audit event and actual Laravel deletion share a transaction. Existing magazine cleanup code is untouched. Organizations and campaign ownership/history are not deleted or transferred. Reassignment alone does not restore visibility; explicit review restores a previously verified profile to verified, or an unverified profile to pending.
- Dedicated organization events retain state changes, private review notes and numeric old/new owner IDs; no deleted-account contact details. Generic admin input logging redacts verification references and review/rejection/suspension reasons.
- Causes are the 20 approved immutable slugs; `OrganizationCauseSeeder` is idempotent and never detaches existing associations. The normal database seeder includes it, but deployment must run only this dedicated seeder after the additive migration; never reset users/categories.
- `config/organizations.php` defaults applications closed. Do not enable `ORGANIZATIONS_APPLICATIONS_OPEN` before phase-three transactional delivery and owner-approved terms are ready. Approved plain-text localized terms belong in `organizations.terms` and their version in `ORGANIZATIONS_TERMS_VERSION`; real submissions cannot accept empty terms. Support uses optional `ORGANIZATIONS_SUPPORT_EMAIL`, then existing `email_to_staff`, then configured sender. Verify the recipient before launch.
- UI is English/Italian/French, with explicit English fallback in every other supported locale. Metadata/canonical/OG image fallback, native sharing, clipboard fallback and a report mailto expose only public profile information.
