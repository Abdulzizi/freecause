# Account onboarding and welcome email

New Google and password registrations are marked as awaiting a welcome email. Google confirms the email address during OAuth; password registrations retain the existing email verification flow.

Before participating, all signed-in users (including legacy accounts) explicitly save their country, gender (including “Prefer not to say”), and an explicit preferred language from the active site languages. The existing `users.locale` stores this preference for subsequent communications; `preferred_language_confirmed_at` records the choice. The language selector does not silently accept the OAuth page language for an account that has never confirmed a preferred language.

After a verified user saves a complete profile, `SendWelcomeEmail` is queued. It uses the saved preferred language at delivery time, retries transient SMTP failures for up to seven days, and defers while SMTP or the provider quota is unavailable. A unique queue job and user row lock prevent repeated profile saves from generating repeated welcome emails. `welcome_email_sent_at` records acceptance by SMTP, not inbox delivery. SMTP delivery is at least once: a worker crash between provider acceptance and the database commit can still cause a retry.

Existing accounts without `preferred_language_confirmed_at` are sent to profile completion before protected actions, even when country, gender and a migrated locale are already present. They must explicitly save their preferred language before signing, creating or commenting. They are not automatically enrolled in welcome email delivery; there is no welcome bulk send and no change to optional product email consent. A permanently failed welcome job remains visible in `failed_jobs` and can be retried after the underlying error is fixed.

Deploy through the standard GitHub pipeline so the additive users-table migration runs before the new release is activated. No credentials are added to source control.


## Transactional email localization and administration

Account verification (including email changes), password reset, welcome, petition milestones, new-signature notices and digests use the recipient’s saved language. Unselected legacy preferences fall back to the stored locale until the user confirms a choice. Browsing public pages stays public. Sign confirmation and shoutbox actions also require a complete profile; logout, recovery, support, unsubscribe and account deletion remain available.

Localized Content contains plain-text email fields for each active language. `emails:seed-templates` stores missing built-in translations in `page_contents` under `page=emails`, without replacing existing edits. On first seeding it preserves the legacy English verification subject, heading, button and footer. Run the command after deploying this change. Rendering falls back to the corresponding translated source defaults if template storage is unavailable. Template variables such as `:name`, `:count`, `:title`, `:url`, `:hours` and `:minutes` must be retained; template text is escaped, never executed as Blade or HTML.

System administrators can save a DeepL API key (encrypted with the application key, not displayed or committed) and use **Save, translate and sync all email languages**. The selected language is the source; one queued job per other active language translates changed fields and atomically saves that language’s fields. Unchanged source fields reuse the saved translations to conserve the free quota. Only the static templates and variable names are sent to DeepL, never recipients, personal profile data or actual verification/reset links. XML ignore tags preserve placeholders. Source changes invalidate pending output, and provider failures or exhausted quota preserve existing templates. This integration never upgrades or purchases a provider plan. As of 2026-11-05 the Developer plan includes one million total free characters; its quota does not renew monthly. Credentials are configured manually in the system-admin form.
